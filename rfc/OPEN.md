# Open questions found during implementation

Add one entry per ambiguity, with the RFC section and the interpretation chosen.

Draft 0.3 resolved every question found while building milestone 1, and draft 0.4 what the first head and the first tooling found; `rfc/CHANGELOG.md` says where each answer went. This file holds only what is still open. The design questions listed in RFC §14 (last-visit cursor, withdraw, delegation rules, retention, head-to-head trust, content hash, field name) are tracked there, not here.

1. **§7.2 — surfacing parked changes.** A producer MUST report a parked change, at least by logging, and a head MAY offer a way to surface it to the person, but no mechanism is defined. Should a producer report a parked change as a card of its own (for example a `kind: signal` in the parked card's thread), or should the head expose an endpoint? **Current:** the client calls `onParked` and logs by default; nothing reaches the person.
2. **§3 — typed extension fields in the file form.** Fields that neither the protocol nor an implemented extension defines are strings in the file form, so an extension field such as `orders.claim_seq` does not survive a trip through a file. How does an extension declare its field types so a file reader can type them? **Current:** such producers send the wire form.
3. **§14 — fixtures that only apply to some heads.** R07 (render cache) applies only to heads that pre-render, and SHOULD-level fixtures (C24) may fail without breaking conformance. A head cannot yet declare which conditional fixtures apply to it, so a runner relies on its caller (`conformanceSuite({ should: false })`, or skipping R07 by hand). Should the description (§7.5) carry this, for example `render.prerender: true`?
4. **§4.2, §7.4 — refusals for owner-side actions.** Presenting and acknowledging a card are done through the head's own interface, not a protocol operation, yet `not_acknowledgeable` is in the normative code table. Should the table list only codes that can appear on protocol responses? **Current:** listed and marked as for the head's interface.
5. **§14 — refusals the suite still does not cover.** The first head found no fixture for `id_mismatch` (URL id ≠ card id), `wrong_person` (§10), or `404` on the owner's seen and acknowledge. 0.4 adds fixtures for `401`, `413`, `invalid_cursor` and the describe body only. **Current:** covered by each head's own HTTP tests.
6. **§14 — an asynchronous test clock.** `HeadUnderTest.clock.set()` is synchronous, so an HTTP adapter has to queue the value and flush it before its next request. Widening it to `void | Promise<void>` (and awaiting it in the runner) would not break existing adapters. **Current:** unchanged; 0.4 extended `HeadUnderTest` only where C25–C31 needed it.
7. **§9 — `delivery` and the person's later actions.** `delivery` is fixed when the content is stored; raising or lowering a ceiling does not revisit stored cards, and nothing lets the person move one card (say from `log` to `brief`). Is that a head-interface matter, or should a later owner-side change of `delivery` take a new `change_seq` and be visible to the producer? **Current:** set on store only.

## Orders

Found while implementing Appendix A in `@pbcp/core` (`orders.ts`), the fixtures C16–C20, C32, C33, and the executor in `@pbcp/client`. These are inputs for draft 0.5; the RFC text is unchanged.

8. **A.2, A.5, §7.4 — claim refusals have no codes, and 409 has no body rule.** A.5 says a `410` carries the order; A.2 says nothing about the `409` body; §7.4 lists no code for either, and its error-body rule ("every refusal that does not return a card") would need one. **Current:** both `409` and `410` return the order card, like the locked-card `409` of §7.1, with no error body. Clients name them `lease_held` (409) and `order_terminal` (410); the MCP adapter reports those codes.
9. **A.1, A.2 — claiming what you cannot read.** No status for a claim by a producer the order is not addressed to (or a wildcard order it was not eligible for), or on a card that is not an order. **Current:** `404 not_found`, the same as an id the head does not hold: the caller cannot read it (A.1), so it is not there for it (C20).
10. **A.2 — the claim request.** No bounds for `lease_seconds` and no code for a missing or malformed one. **Current:** a positive integer; anything else is `400` (`invalid_card` in the in-process adapter, for want of a better code); the upper bound is the head's.
11. **A.3 — success or failure.** `claimed` → `done` on a "success" outcome and → `failed` on a "failure", but nothing on the card says which. A.4's sketch makes a failure a decision card ("retry / abandon?") while A.3 says a decision outcome is often a success ("here is the draft, approve?"), so `kind` cannot tell. **Current:** the extension field `orders.result: "failed"` marks a failure; absent (or `"done"`) is success, whatever the kind.
12. **A.3 — "the currently valid lease".** Is a matching `orders.claim_seq` enough, or must the outcome also come from the lease holder, and while the lease is live? **Current:** all three: the order is `claimed`, the outcome's producer is `claimed_by`, its `orders.claim_seq` is the order's `claim_seq`, and its `references` name the order. The head applies expiry first, so an outcome after a lapsed lease is stale even if nobody re-claimed.
13. **A.5 vs A.3 — why an outcome after a cancel is ignored.** A.5 says the executor's final outcome after a `410` has a stale `orders.claim_seq`, but cancelling does not change `claim_seq`; the outcome is ignored because the order is `cancelled` (A.3). **Current:** as A.3; A.5's parenthesis is worded wrongly.
14. **A.1, A.3 — renewals move `claim_seq`.** Every renewal increments `claim_seq`, and only the current value moves `exec_state`, so an outcome must carry the value of the executor's latest renewal; a renewal that lands after the outcome was built makes it stale. **Current:** the executor serialises renewals and waits for any in flight before it builds the outcome. Should a renewal by the holder keep `claim_seq` instead?
15. **A.2, §7.2 — when expiry becomes visible.** "The order returns to `open`" needs a new `change_seq` to reach sync, but the head owns no timer in the protocol. **Current:** the head applies expiry lazily before any read or write that involves the order (sync, claim, an outcome), assigning the new `change_seq` then. The SHOULD signal to the person on expiry is not implemented by the in-process adapter.
16. **A.1 — dismissing a finished order.** A.1 cancels an `open` or `claimed` order; it does not say whether a `done` or `failed` order can be dismissed. **Current:** it can: `state` becomes `decided`, `exec_state` stays as it was. Any other decision on an order (including `edited` and `delegated`) is `400 invalid_decision`.
17. **A.1 — the order card's other fields.** The schema overrides say nothing about `urgency`, `delivery` (§4.2, new in 0.4), `thread` or `source` on an order. **Current:** `producer: head`, `title` and `body` from the person, `urgency` optional, `delivery` as for any card (default `brief`), no `thread`.
18. **A.4 — one outcome id per order, not per claim.** `me:order:<ulid>:outcome` is the same for every claim, so after a lapsed lease the second run's outcome re-PUTs the first one's id: it replaces it if still open, is `409` if the person decided it. **Current:** as written; the replacing outcome is applied (A.3) when stored.
19. **A.1 — wildcard eligibility is head-private.** The set of executors eligible when a `*` order was minted must be kept but is "not discoverable through the protocol", so it cannot live on the card. **Current:** `mintOrder` returns it beside the order and `visibleTo(order, root, eligible)` takes it as an argument; the head stores it where producers cannot read it.
20. **A.3 — order of `change_seq` for an outcome.** An accepted outcome changes two cards (the outcome and the order); §7.2 orders supersession (predecessor first) but not this. **Current:** the outcome takes the lower value, the order the higher.
21. **A.1 — named orders and executors.** A named `to_producer` reaches that producer whether or not the head counts it as an executor; only `*` depends on executor status (C16). Stated nowhere explicitly.

# Open questions found during implementation

Add one entry per ambiguity, with the RFC section and the interpretation chosen.

Draft 0.3 resolved every question found while building milestone 1, and draft 0.4 what the first head and the first tooling found; `rfc/CHANGELOG.md` says where each answer went. This file holds only what is still open. The design questions listed in RFC §14 (last-visit cursor, withdraw, delegation rules, retention, head-to-head trust, content hash, field name) are tracked there, not here.

1. **§7.2 — surfacing parked changes.** A producer MUST report a parked change, at least by logging, and a head MAY offer a way to surface it to the person, but no mechanism is defined. Should a producer report a parked change as a card of its own (for example a `kind: signal` in the parked card's thread), or should the head expose an endpoint? **Current:** the client calls `onParked` and logs by default; nothing reaches the person.
2. **§3 — typed extension fields in the file form.** Fields that neither the protocol nor an implemented extension defines are strings in the file form, so an extension field such as `orders.claim_seq` does not survive a trip through a file. How does an extension declare its field types so a file reader can type them? **Current:** such producers send the wire form.
3. **§14 — fixtures that only apply to some heads.** R07 (render cache) applies only to heads that pre-render, and SHOULD-level fixtures (C24) may fail without breaking conformance. A head cannot yet declare which conditional fixtures apply to it, so a runner relies on its caller (`conformanceSuite({ should: false })`, or skipping R07 by hand). Should the description (§7.5) carry this, for example `render.prerender: true`?
4. **§4.2, §7.4 — refusals for owner-side actions.** Presenting and acknowledging a card are done through the head's own interface, not a protocol operation, yet `not_acknowledgeable` is in the normative code table. Should the table list only codes that can appear on protocol responses? **Current:** listed and marked as for the head's interface.
5. **§14 — refusals the suite still does not cover.** The first head found no fixture for `id_mismatch` (URL id ≠ card id), `wrong_person` (§10), or `404` on the owner's seen and acknowledge. 0.4 adds fixtures for `401`, `413`, `invalid_cursor` and the describe body only. **Current:** covered by each head's own HTTP tests.
6. **§14 — an asynchronous test clock.** `HeadUnderTest.clock.set()` is synchronous, so an HTTP adapter has to queue the value and flush it before its next request. Widening it to `void | Promise<void>` (and awaiting it in the runner) would not break existing adapters. **Current:** unchanged; 0.4 extended `HeadUnderTest` only where C25–C31 needed it.
7. **§9 — `delivery` and the person's later actions.** `delivery` is fixed when the content is stored; raising or lowering a ceiling does not revisit stored cards, and nothing lets the person move one card (say from `log` to `brief`). Is that a head-interface matter, or should a later owner-side change of `delivery` take a new `change_seq` and be visible to the producer? **Current:** set on store only.
